# 架构设计

## 一、系统拓扑

```
                        ┌─────────────────────────┐
   海外用户              │  web (Next.js)          │
   Claude Code ─────────►│  Vercel                 │
   Cursor / SDK          │  落地页/控制台/文档/BFF   │
        │                └───────┬─────────────────┘
        │                        │
        │                        ├──► Postgres (Supabase/Neon)
        │                        │      users / orders / ledger
        │                        │
        │                        ├──► Creem / Paddle  (收款)
        │                        │
        │                        └──► new-api 管理 API
        │                               (建用户/建key/加额度/拉日志)
        │
        │  api.你的域名.com
        ▼
┌────────────────────────────────┐
│  new-api  (Docker, 美西 VPS)    │
│  鉴权 → 限流 → 扣费 → 转发       │
└────────────┬───────────────────┘
             ├─ 渠道1  泽西同学(HK)      权重 100
             └─ 渠道2  Anthropic 官方     权重 0  ← 兜底待命

┌────────────────────────────────┐
│  ops (VPS cron)                 │
│  余额监控 → 三级告警 → 熔断降级   │
└────────────────────────────────┘
```

**核心原则:new-api 对用户完全不可见。** 用户只接触 `api.你的域名.com` 和你的英文界面。

## 二、三条关键数据流

### 流程 A:用户发起 API 请求(最高频)

```
Claude Code
  │ ANTHROPIC_BASE_URL=https://api.你的域名.com
  ▼
new-api ─┬─ 1. 校验 API Key
         ├─ 2. 检查限流(RPM/TPM/日额度)
         ├─ 3. 按 max_tokens 预扣额度
         ├─ 4. 转发到渠道1(泽西同学)
         │      └─ 失败 → 自动切渠道2(官方)
         ├─ 5. 收到响应,按实际 usage 结算,回补差额
         └─ 6. 写日志(token数/耗时/模型,不存 prompt 内容)
```

⚠️ **流式请求断流**:拿不到最终 usage,按已产出 token 估算扣费,不能白送。

### 流程 B:用户充值

```
用户点充值 $50
  │
  ▼
web /api/checkout ──► Creem 托管结账页 ──► 用户刷卡
                                              │
                                              ▼
                          Creem ──webhook──► web /api/webhook/creem
                                                    │
                          ┌─────────────────────────┤
                          │ 1. 验签(必须)             │
                          │ 2. 查 orders 表去重 ⚠️幂等 │
                          │ 3. 写 orders + ledger    │
                          │ 4. 调 new-api 加额度      │
                          │ 5. 失败则标记待重试        │
                          └──────────────────────────┘
```

⚠️ **幂等靠 `orders.external_id` 唯一索引**。同一订单重复回调必须只加一次钱。

### 流程 C:补货(人工 + 自动监控)

```
ops/balance-monitor (每 30 分钟)
  │
  ├─ 查 new-api 上游渠道余额
  ├─ 算最近 7 天日均消耗
  ├─ 剩余天数 = 余额 / 日均
  │
  ├─ > 20 天  🟢 正常
  ├─ < 10 天  🟡 推送提醒 → 你微信转账给上游 → 上游手动加额度
  ├─ < 5 天   🟠 高频告警
  └─ < 1 天   🔴 自动降级(关注册/下架高价模型/降RPM/切官方渠道)
```

## 三、部署拓扑

| 组件 | 跑在哪 | 为什么 |
|---|---|---|
| `web/` | **Vercel** | 无状态,自带 CDN,部署简单 |
| `new-api` | **美西 VPS**(Docker) | 流式长连接,Serverless 会超时;靠近用户降延迟 |
| Postgres | **Supabase / Neon** | 托管,免运维 |
| `ops/` 监控脚本 | **VPS cron** | 和网关同机,查余额最快 |

⚠️ **网关必须放美西**,不能跟着上游放香港——用户在美国,先到美西再到香港,总延迟反而更可控,且断供时切官方渠道零延迟惩罚。

## 四、用户体系映射

```
你的 Postgres                        new-api
┌────────────────────┐              ┌──────────────────┐
│ users              │              │ user             │
│  id        (你的)   │◄──映射──────►│  id              │
│  email             │  newapi_uid  │  quota  (额度)    │
│  password_hash     │              │  group  (分组)    │
│  newapi_uid  ──────┼──────────────┤                  │
└────────────────────┘              └──────────────────┘
        │                                   │
        │                            ┌──────▼──────┐
        │                            │ token (key) │
        └───► api_keys ─────映射─────►│  id         │
              (名称/日限额/状态)        │  key        │
                                     └─────────────┘
```

- **注册/登录/邮箱验证** → 你的系统
- **额度/Key/日志** → 调 new-api 管理 API
- 明文 API Key **不落你的库**,只存 new-api 的 token id

## 五、安全边界

| 边界 | 措施 |
|---|---|
| 密钥管理 | 全部走 `.env`,`.env` 在 `.gitignore`;Vercel 用环境变量 |
| new-api 管理 API | 只允许 Vercel 的服务端调用,不暴露给浏览器 |
| Webhook | **必须验签**;失败返回 4xx 让平台重试 |
| 用户输入 | 充值金额、key 名称、限额全部服务端校验 |
| 报错 | 面向用户只返回友好文案,原始错误只进日志 |
| 日志 | **不记录 prompt 内容、不记录密钥**,只记 token 数和元信息 |
| 限流 | 每 key RPM/TPM + 每 key 日额度 + 账户日额度,三层都要开 |
