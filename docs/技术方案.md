## 二、技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 网关 | **new-api**(Docker 自部署) | 现成的用户/额度/日志/多渠道/故障转移,不重造 |
| 前台 | **Next.js 15 + TypeScript + Tailwind + shadcn/ui** | 部署简单,组件现成,后续好维护 |
| 部署 | Vercel(前台) + VPS(网关,建议美西) | 前台无状态;网关要长连接,不能用 Serverless |
| 数据库 | **Postgres**(Supabase 或 Neon) | 托管,省运维 |
| 认证 | 邮箱 + Google OAuth | 海外开发者习惯 |
| 支付 | **Creem**(主) + **Paddle**(备) | MoR 模式,免公司主体+免税务合规 |
| 落地账户 | **Payoneer** | 对中国大陆提现支持成熟 |

### 用户体系设计(关键决策)

**不用 new-api 的原生用户系统**,改为:

```
你的 Postgres              new-api
┌──────────────┐          ┌──────────────┐
│ users        │          │ new-api user │
│  id          │◄────────►│  id          │
│  email       │  映射     │  quota       │
│  newapi_uid  │          │  tokens      │
└──────────────┘          └──────────────┘
```

- 注册/登录/邮箱验证 → **你的系统**
- 额度/Key/日志 → **调 new-api 管理 API**
- 用户永远看不到 new-api 的界面

**理由**:new-api 的用户系统是中文体系,字段和流程不好定制;而额度和日志这些核心能力它做得很好,没必要重写。

## 三、数据模型(Postgres)

| 表 | 职责 | 关键约束 |
|---|---|---|
| `users` | 账号、邮箱、new-api 用户 ID 映射 | email 唯一 |
| `orders` | 支付订单:金额、通道、状态、外部订单号 | **外部订单号唯一(幂等靠它)** |
| `credit_ledger` | 额度流水:充值(+)、消费(−)、退款(−) | **append-only,只加不改** |
| `api_keys` | key 元信息(名称、日限额、状态) | 明文 key 不落库,只存 new-api token id |
| `usage_daily` | 每日用量汇总(从 new-api 日志聚合) | 按 user+day+model 唯一 |

⚠️ **`credit_ledger` 必须 append-only**:余额 = 流水求和,不存余额字段。
这是这类系统最容易翻车的地方——并发下改余额字段必然对不上账。

## 四、计费与定价

### 定价策略
**售价 = 官方价 × 30%**(官方 3 折)

| | 成本 | 售价 | 毛利率 |
|---|---|---|---|
| Opus 4.8 输入 | $0.306/M | $1.50/M | **79.6%** |
| Opus 4.8 输出 | $1.528/M | $7.50/M | **79.6%** |

不打更低,原因:价格低到离谱会引起用户怀疑,也更容易触发支付平台风控。

### 充值档位
**$20 / $50 / $200**,最低 $20。

理由:MoR 有固定手续费($0.40-0.50),$5 小额充值实际费率高达 15%。

### 扣费机制(必须做对)
1. **预扣**:请求前按 `max_tokens` 预扣上限,结束后按实际用量回补
2. **流式兜底**:SSE 断流拿不到最终 usage,按已产出 token 估算扣费
3. **缓存分开计价**:cache read / cache write 单独算(Claude Code 场景 90% 成本在这)
4. **三层限流**:每 key RPM/TPM + 每 key 日额度 + 账户日额度上限

## 五、补货与告警(运营核心)

上游只能人工转账补货,所以必须做库存管理:

| 水位 | 阈值 | 动作 |
|---|---|---|
| 🟢 充足 | > 20 天用量 | 正常 |
| 🟡 预警 | < 10 天用量 | 推送提醒你去转账 |
| 🟠 告警 | < 5 天用量 | 高频告警(Telegram+邮件+推送) |
| 🔴 熔断 | < 1 天用量 | **自动降级**(见下) |

⚠️ **20 天不是 14 天**:Creem 每月只在 1 号和 15 号打款,最长等 15 天才拿到钱。

### 🔴 熔断必须是"降级"不是"挂掉"
用户能接受变慢,不能接受 500 —— **报错会直接导致拒付**。

降级顺序:
1. 关闭新用户注册 + 关闭自动充值
2. 高价模型(Opus/Fable)临时下架,只留 Haiku/Sonnet
3. RPM 降到 1/3,返回 `429 + Retry-After`(**不是 500**)
4. 首页挂 status 提示
5. 归零前切换到 Anthropic 官方渠道兜底

### 为什么官方兜底划算
毛利 80% 时:正常跑 3 天的利润,够兜底 1 天。
断供一天的口碑损失和拒付,远比这个贵。
→ **官方渠道 M1 就要配好,权重设 0 待命。**

## 六、风险对冲清单

| 风险 | 对冲措施 | 优先级 |
|---|---|---|
| 上游断供 | new-api 多渠道 + 官方 API 兜底 | **M1 必做** |
| 余额耗尽 | 三级水位告警 + 自动降级熔断 | **M1 必做** |
| 预付款损失 | 分批小额充值,余额只留 20-30 天用量 | 运营纪律 |
| 支付平台封号 | Creem + Paddle 双通道,支付层可插拔 | M2 |
| 用户拒付 | 主动退款政策(未消费 credits 30 天全额退) | M2 |
| 结汇额度 | 只结汇成本部分(20%),利润留境外;年限 $5 万跨平台合并计算 | 运营纪律 |
